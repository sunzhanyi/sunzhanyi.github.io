在给项目中的功能编写单元测试时，有时会遇到：为了验证某个业务分支，测试代码开始模拟完整运行环境，通常这种情况会让测试代码变得晦涩而且越来越难维护。

最近在对一个 Go 项目进行重构时，就遇到了这个问题。借此机会复盘一下，看看如何通过职责分离与依赖注入，重新划清单测的边界。

### 测试反模式：被“全局环境”绑架的单测

写单元测试时，测试对象需要在特定的环境下才能运行，于是就通过各种方式来模拟测试对象需要的环境，典型表现包括：

- 通过修改全局变量环境来模拟环境
- 通过反射、unsafe 或类似手段修改第三方包的私有状态来模拟环境
- 为了触发环境分支测试，直接从外层 API 函数切入测试

最终不但使测试代码晦涩难懂而且在测试失败后，难以判断是业务逻辑错误，还是环境模拟失败，增加CI（持续集成）过程的问题排查复杂度。

下面是一个简化的案例：
```go
func HandleRequest(ctx context.Context, req *Request) (*Response, error) {
	if env.IsOverseas() {
		return handleOverseas(ctx, req)
	}
	return handleDomestic(ctx, req)
}
```

<!-- 代码包含两套逻辑：根据不同的环境，处理不同业务。 -->

这个 API 通过环境检查处理两套逻辑。

需要注意的是 HandleRequest 是请求入口，如果测试目标是验证 handleOverseas 的业务行为，那么测试就必须让 env.IsOverseas() 返回 true，换句话说，需要通过某种方式修改环境这个全局变量。

于是，测试很自然就变成：
``` go
func TestOverseasLogic(t *testing.T) {
	forceSetGlobalEnv("overseas")
	defer restoreGlobalEnv()

	resp, err := HandleRequest(ctx, req)
	assertOverseasResponse(t, resp, err)
}
```

<!-- 这种写法看上去覆盖了目标分支逻辑，实际却把单测边界扩大到了环境路由层，甚至运行环境本身。 -->


### 职责耦合与测试边界的错位

#### 被测对象不清晰

单测首先要明确被测对象到底是什么：

- 是业务逻辑本身？
- 是入口函数的环境分发逻辑？
- 是环境配置是否正确？

这三类目标对应不同测试方式。

如果测试目标是业务逻辑，就应该直接测试业务逻辑对象；如果目标是入口分发，就应该只验证分发是否正确；如果目标是环境配置正确性，则不应放在普通单测中。

很多问题的根源在于：测试本来想测业务逻辑，但实际从入口函数切入，导致不得不模拟环境。

#### 业务逻辑和路由逻辑混在同一层

当代码被组织程这样时：

```text
api/
 handler.go // 判断环境 + 调用国内/海外逻辑
 overseas_logic.go // 海外业务实现
```

API 层同时承担了两个职责：

- 判断当前环境，决定走哪个分支
- 实现具体业务

这种结构会让测试天然倾向于从 API 入口进入。一旦从入口进入，环境判断就会成为测试前置条件，单测就容易被迫模拟环境。

#### 环境正确性被误放进单测

环境配置是否正确，例如：

- 地域是否与环境对应
- 配置文件是否被正确加载

这些属于配置或部署正确性，不属于普通业务单测的责任。

业务单测需要测试：

- 当业务依赖已经明确具体的环境，业务行为是否正确
- 直接执行业务逻辑时，计算、读写、返回结构是否正确


### 重构边界与依赖注入实践

#### 1. 确定单测边界

如果当前测试目标是海外业务实现，就不应从入口函数切入，而应直接调用海外实现函数或业务对象。

不推荐：

```go
func TestOverseasBehavior(t *testing.T) {
	forceSetGlobalEnv("overseas")
	defer restoreGlobalEnv()

	resp, err := HandleRequest(ctx, req)

	assertOverseasResponse(t, resp, err)
}
```
深入应用 AI 工具（如 Harness/Cursor 等）重塑开发流，专注于高复杂度代码生成与深度 Code Review。理解 AI 工程化底层原理与 CI/CD 集成逻辑，能够高效协同平台团队落地自动化流程，利用 AI 显著提升代码交付质量与研发人效
推荐：

```go
func TestOverseasBehavior(t *testing.T) {
	manager := &OverseasManager{
		Repo: mockRepo,
		UserClient: mockUserClient,
		DataClient: mockDataClient,
	}

	resp, err := manager.Handle(ctx, req)

	assertOverseasResponse(t, resp, err)
}
```

这样测试只关注海外业务行为，不再依赖环境模拟。

#### 2. 保持 API 简单

应用程序接口只需要处理：

- 参数解析
- 身份或上下文提取
- 根据环境选择业务实现

```go
func HandleRequest(ctx context.Context, req *Request) (*Response, error) {
	if env.IsOverseas() {
		return overseasManager.Handle(ctx, req)
	}
	return domesticClient.Handle(ctx, req)
}
```

如果需要验证路由，也只需要增加一个简单的 mock 对象来模拟环境分支的逻辑：

```go
func TestHandleRequest_RouteToOverseas(t *testing.T) {
	envChecker := mockEnvChecker{overseas: true}
	overseasManager := mockOverseasManager{}

	handler := &Handler{
		EnvChecker: envChecker,
		OverseasManager: overseasManager,
	}

	_, _ = handler.HandleRequest(ctx, req)

	assertCalled(t, overseasManager)
}
```

#### 3. 业务逻辑移到 manager 层

其实，单测的边界混乱不清，根本的原因还是代码组织设计有问题。对于上面的代码，更合理的组织方式是：

```text
api/
 handler.go

lib/
 manager/
 overseas_manager.go
```
把业务封装到单独的管理器中，通过 interface 对外提供接口，这就把单测的边界限制在管理器中，让业务和单测的边界变得更加清晰。

定义完整接口：

```go
type OverseasManager interface {
	Handle(ctx context.Context, req *Request) (*Response, error)
	Preview(ctx context.Context, req *PreviewRequest) (*PreviewResponse, error)
	Update(ctx context.Context, req *UpdateRequest) (*UpdateResponse, error)
}
```

在实现层中，通过依赖注入获得 DAO、RPC client 等其他基础能力：

```go
type OverseasManager struct {
	repo Repository
	userClient UserClient
	dataClient DataClient
}

func (m *OverseasManager) Handle(ctx context.Context, req *Request) (*Response, error) {
	// overseas business logic
}
```


### 总结

环境依赖类单测最重要的是先划清边界。如果测试目标是业务实现，就直接测试业务实现；如果测试目标是入口路由，就只测试分发；如果测试目标是环境配置正确性，就不要放在普通单测里。

更推荐的设计是：API 层负责路由，Manager 层负责业务，环境判断停留在入口边界，单测主要覆盖 Manager，环境配置正确性交给集成测试或配置校验。

对应原则可以概括为：
不要在单测里伪造完整运行环境；
把环境作为边界条件处理；
把业务逻辑放在可直接测试的对象中。

这样可以减少全局状态污染、降低 mock 维护成本，也能让测试失败时更容易定位到真正的业务问题。
