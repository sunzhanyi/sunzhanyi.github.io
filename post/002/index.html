环境依赖类单测的边界治理#

一、问题#

在环境依赖类业务中，单测经常会出现一个误区：为了验证某个业务分支，测试代码开始模拟完整运行环境。

典型表现包括：

  • 通过修改全局变量模拟不同地域、机房或环境。
  • 通过反射、unsafe 或类似手段修改第三方包的私有状态。
  • 为了触发某个入口分支，从较外层 API 函数切入测试。
  • 测试文件引入大量与当前测试目标无关的 mock。
  • 测试失败后，难以判断是业务逻辑错误，还是环境模拟失败。

例如，一个服务存在国内和海外两套逻辑：

func HandleRequest(ctx context.Context, req *Request) (*Response, error) {
	if env.IsOverseas() {
		return handleOverseas(ctx, req)
	}
	return handleDomestic(ctx, req)
}

如果测试目标是验证 handleOverseas 的业务行为，却从 HandleRequest 入口切入，那么测试就必须让 env.IsOverseas() 返回 true。

这时测试很容易变成：

func TestOverseasLogic(t *testing.T) {
	forceSetGlobalEnv("overseas")
	defer restoreGlobalEnv()

	resp, err := HandleRequest(ctx, req)

	assertOverseasResponse(t, resp, err)
}

这种写法表面上覆盖了海外逻辑，实际却把单测边界扩大到了环境路由层，甚至运行环境本身。

二、原因#

1. 被测对象不清晰#

单测首先要明确被测对象到底是什么：

  • 是海外业务逻辑本身？
  • 是入口函数的环境分发逻辑？
  • 是环境配置是否正确？

这三类目标对应不同测试方式。

如果测试目标是业务逻辑，就应该直接测试业务逻辑对象；如果目标是入口分发，就应该只验证分发是否正确；如果目标是环境配置正确性，则不应放在普通单测中。

很多问题的根源在于：测试本来想测业务逻辑，但实际从入口函数切入，导致不得不模拟环境。

2. 业务逻辑和路由逻辑混在同一层#

当代码结构类似下面这样时，测试很容易写偏：

api/
 handler.go // 判断环境 + 调用国内/海外逻辑
 overseas_logic.go // 海外业务实现

API 层同时承担了两个职责：

  • 判断当前环境，决定走哪个分支。
  • 承载具体业务实现。

这种结构会让测试天然倾向于从 API 入口进入。一旦从入口进入，环境判断就会成为测试前置条件，单测就容易被迫模拟环境。

3. 环境正确性被误放进单测#

环境配置是否正确，例如：

  • 某个地域是否属于海外。
  • 某个 IDC 是否映射到正确业务区域。
  • 某个配置文件是否被正确加载。

这些属于配置或部署正确性，不属于普通业务单测的责任。

业务单测更适合验证：

当业务依赖告诉我当前是海外时，业务行为是否正确。
当直接执行海外业务逻辑时，计算、读写、返回结构是否正确。

而不是验证：

当前真实运行环境是否被识别为海外。

4. mock 所有权不清晰#

如果测试中为了某个外部接口手工生成一个大 mock，并放在具体业务目录下，也会带来维护问题：

  • mock 与接口定义分离，接口升级后容易失效。
  • 文件体积大，污染当前业务测试目录。
  • 其他业务包无法复用。
  • 当前测试未使用时，容易变成冗余代码。

mock 的位置应尽量跟随接口所有权。接口在哪个包定义，mock 最好由哪个包统一提供。

三、修改#

1. 收窄当前单测边界#

如果当前测试目标是海外业务实现，就不应从入口函数切入，而应直接调用海外实现函数或业务对象。

不推荐：

func TestOverseasBehavior(t *testing.T) {
	forceSetGlobalEnv("overseas")
	defer restoreGlobalEnv()

	resp, err := HandleRequest(ctx, req)

	assertOverseasResponse(t, resp, err)
}

推荐：

func TestOverseasBehavior(t *testing.T) {
	manager := &OverseasManager{
		Repo: mockRepo,
		UserClient: mockUserClient,
		DataClient: mockDataClient,
	}

	resp, err := manager.Handle(ctx, req)

	assertOverseasResponse(t, resp, err)
}

这样测试只关注海外业务行为，不再依赖环境模拟。

2. API 层只保留薄分发逻辑#

入口层应尽量只做三件事：

  • 参数解析。
  • 身份或上下文提取。
  • 根据环境选择业务实现。

示例：

func HandleRequest(ctx context.Context, req *Request) (*Response, error) {
	if env.IsOverseas() {
		return overseasManager.Handle(ctx, req)
	}
	return domesticClient.Handle(ctx, req)
}

这类入口函数本身不应承载复杂业务逻辑。

如果要测入口层，只需要覆盖非常薄的分发行为：

func TestHandleRequest_RouteToOverseas(t *testing.T) {
	envChecker := mockEnvChecker{overseas: true}
	overseasManager := mockOverseasManager{}

	handler := &Handler{
		EnvChecker: envChecker,
		OverseasManager: overseasManager,
	}

	_, _ = handler.HandleRequest(ctx, req)

	assertCalled(t, overseasManager)
}

这类测试数量应少，重点是验证路由，而不是重复验证海外业务细节。

3. 将业务逻辑下沉到 manager 层#

更合理的结构是：

api/
 handler.go

lib/
 manager/
 overseas_manager.go

定义完整接口：

type OverseasManager interface {
	Handle(ctx context.Context, req *Request) (*Response, error)
	Preview(ctx context.Context, req *PreviewRequest) (*PreviewResponse, error)
	Update(ctx context.Context, req *UpdateRequest) (*UpdateResponse, error)
}

实现层通过依赖注入获得 DAO、RPC client 或其他基础能力：

type overseasManager struct {
	repo Repository
	userClient UserClient
	dataClient DataClient
}

func (m *overseasManager) Handle(ctx context.Context, req *Request) (*Response, error) {
	// overseas business logic
}

这样单测可以直接构造 manager，并 mock 它真正依赖的外部组件。

4. 删除无用或位置不合理的 mock#

对于未使用的本地大 mock，应直接删除。

如果后续确实需要测试国内分支，应优先在接口定义方生成统一 mock，例如：

external/service/client/mock_client.go

业务测试中直接使用：

client.NewMockServiceClient(ctrl)

而不是在具体业务目录下临时生成一份完整 mock。

5. 环境配置正确性放到更合适的位置#

环境配置类验证建议放在：

  • 配置校验脚本。
  • 启动阶段自检。
  • 集成测试。
  • E2E 测试。
  • 部署前检查。

普通单测只关心边界内逻辑，不负责证明真实环境配置是否正确。

四、总结#

环境依赖类单测最重要的是先划清边界。

如果测试目标是业务实现，就直接测试业务实现；如果测试目标是入口路由，就只测试分发；如果测试目标是环境配置正确性，就不要放在普通单测里。

这类问题通常不是“如何更优雅地模拟环境”，而是代码职责和测试边界没有对齐。

更推荐的设计是：

API 层负责路由。
Manager 层负责业务。
环境判断停留在入口边界。
单测主要覆盖 manager。
环境配置正确性交给集成测试或配置校验。

对应原则可以概括为：

不要在单测里伪造完整运行环境；
把环境作为边界条件处理；
把业务逻辑放在可直接测试的对象中。

这样可以减少全局状态污染、降低 mock 维护成本，也能让测试失败时更容易定位到真正的业务问题。
