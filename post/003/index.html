gRPC -> HTTP -> TCP 三层超时排查实录#

1. 问题背景#

一次和风天气气压接口调用出现偶发错误：

Get "https://xiaomi-hope-api.qweather.net/v7/grid-weather/24h?lang=zh-hans&location=80.65%2C16.41&unit=m": dial tcp 172.104.38.93:443: i/o timeout

现象有几个关键点：

  • 调用失败概率不高，说明网络整体是通的，不是完全不可达。
  • 变更点主要是 fallback 域名对应的 IP 从旧节点切到了新节点。
  • 旧 IP 172.104.37.202 也有失败，但新 IP 172.104.38.93 在高峰期失败率约为旧 IP 的两倍。
  • 单次失败请求的整体耗时只有约 510ms，不是常见的 5s 或 30s 超时。

日志时间线：

10:19:33.110 hefeng cache miss，准备请求和风
10:19:33.110 domain 从 https://nn7fby8wfm.yun.qweatherapi.com 切换到 https://xiaomi-hope-api.qweather.net
10:19:33.110 创建 flowtoken：ft-https://xiaomi-hope-api.qweather.net
10:19:33.612 HTTP 请求报错：dial tcp 172.104.38.93:443: i/o timeout
10:19:33.612 SESSION 日志：cost=510ms，domain=https://xiaomi-hope-api.qweather.net:500

从时间线看，真正触发的是约 500ms 的连接阶段超时，而不是业务整体超时。

3. 三层超时设置#

3.1 gRPC 客户端超时#

gRPC 超时是客户端侧的 deadline。当前项目作为 server，不在本仓库中直接设置调用方的 deadline，但框架默认客户端超时可以在依赖中看到：

// grpcresolving@v0.12.2/resolving.go
func DefaultClient(...) (*grpc.ClientConn, error) {
 return DefaultClientTimeout(..., 1*time.Second)
}

实际超时拦截器逻辑：

// grpcresolving@v0.12.2/interceptor/timeout.go
if _, ok := ctx.Deadline(); !ok {
 ctx, cancel = context.WithTimeout(ctx, defaulttimeout)
 defer cancel()
}

这层超时控制的是一次 RPC 从客户端视角最多等待多久。它不等同于服务端内部 HTTP 请求的 dial timeout。

本次日志里 SESSION 正常打印，整体耗时 510ms，说明这次请求没有被 gRPC 1s deadline 提前打断。

3.2 HTTP Client 整体超时#

和风请求处设置了 HTTP client 的整体超时：

// lib/service/weather_service_v3.go
client := &commonhttpclient.HttpClient{
 Domain: srv.getHFDomain(),
 Timeout: time.Second * time.Duration(srv.TimeOut),
}

默认 srv.TimeOut 来自：

// lib/consts/weather_basics.go
HttpTimeOut = 5

所以这层通常是 5s。它覆盖 DNS、TCP connect、TLS handshake、请求发送、响应头等待、响应体读取等整体阶段。

但本次日志约 500ms 就失败，说明不是 HTTP overall timeout 先触发。

3.3 TCP DialTimeout#

commonhttpclient 底层使用 transportpool 创建 http.Transport：

// commonhttpclient/client.go
c.client = &http.Client{
 Transport: transportpool.NewTransportPoolWithConf(c.Conf),
 Timeout: c.Timeout,
}

transportpool 的默认 TCP 连接超时是 500ms：

// transportpool/transport.go
dialTimeout := conf.HttpPoolDialTimeoutInMs
if dialTimeout > 0 {
 tout = time.Duration(dialTimeout) * time.Millisecond
} else {
 tout = 500 * time.Millisecond
}

callHeFeng 没有传自定义 Conf，所以 HttpPoolDialTimeoutInMs 是零值，最终走默认 500ms。

本次日志中的 domain=...:500 与 dial tcp ... i/o timeout 高度吻合：TCP connect 阶段约 500ms 没建立成功，于是返回 i/o timeout。

4. 这次为什么不是简单归因于客户端配置#

排查过程中容易误判为“客户端 500ms 太短”。但结合上下文，更合理的判断是：变更后的域名/IP 节点质量变差，导致在既有工程阈值下失败率上升。

理由：

  • 500ms 是框架默认值，不是本次改动临时写出来的魔法数字。
  • 本服务内其他 HTTP 调用长期使用同一套 commonhttpclient + transportpool 机制。
  • 变更点是 fallback domain 指向的新 IP，而不是客户端超时参数。
  • 旧 IP 172.104.37.202 也有失败，但新 IP 172.104.38.93 失败率明显更高，说明新节点的连接建立耗时分布更差。
  • 如果客户端默认 500ms 本身完全不合理，问题应当更早、更广泛地在其他 HTTP 调用中暴露。

所以结论不是“客户端写错了 500ms”，而是：

新 fallback IP 在高峰期更容易超过当前工程默认的 TCP connect 预算，导致 dial timeout 增多。

这更偏向服务端节点、网络路径、DNS 调度或供应商侧容量问题。

5. 附带发现：callHeFeng 的 HttpClient 用法特殊#

当前代码里有两类 HttpClient 用法。

第一类是在服务启动时创建并复用：

// lib/service/weather_service_v3.go
srv.httpClient = &commonhttpclient.HttpClient{
 Domain: weatherConf.Endpoint,
 Timeout: time.Duration(srv.TimeOut) * time.Second,
}

第二类是 callHeFeng 每次请求都创建：

// lib/service/weather_service_v3.go
client := &commonhttpclient.HttpClient{
 Domain: srv.getHFDomain(),
 Timeout: time.Second * time.Duration(srv.TimeOut),
}

这会带来两个现象：

  • 每次请求都会创建新的 FlowToken，日志里能看到 create flowtoken ... 和 [FlowToken] startup。
  • 每次请求都会创建新的 transport pool，连接复用收益有限。

这不是本次问题的唯一根因，因为旧 IP 在同样写法下失败率更低；但它会放大连接建立阶段的不稳定性。长期优化可以考虑为和风域名维护独立、可复用的 HTTP client。

示例包含三组实验：

  • 演示 http.Client.Timeout = 5s 与底层 Dialer.Timeout = 500ms 同时存在时，谁先到期谁先返回。
  • 模拟 gRPC deadline 与 HTTP 调用的关系：HTTP 请求绑定上游 context 时会随 deadline 取消；不绑定 context 时则继续由 HTTP/Dial 超时控制。

7. 排查结论#

本次问题不是 gRPC 超时，也不是 HTTP overall timeout，而是 TCP connect 阶段触发了 transportpool 默认的 500ms dial timeout。

更准确的归因是：fallback 域名切换到新 IP 后，新 IP 在高峰期 TCP 连接建立耗时分布变差，超过既有 500ms 工程预算的概率上升。因此失败率变高。

建议后续排查方向：

  • 对比两个 IP 的 TCP connect 耗时分布，而不是只看平均请求耗时。
  • 联系和风/域名提供方确认 172.104.38.93 节点负载、路由、连接队列和 DNS 调度策略。
  • 在 Nacos 中评估是否回滚 fallback domain，或切回主域名 https://nn7fby8wfm.yun.qweatherapi.com。
  • 长期优化 callHeFeng 的 HTTP client 复用方式，降低每次请求都重新建连接池和 FlowToken 的成本。
